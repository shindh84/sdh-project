# 데이터와 인증

## Decisions

- 사용자 계정, 전시 데이터, 사진 파일은 Supabase 하나로 해결한다. Postgres와 인증과 파일 저장소를 각각 다른 서비스로 조합하지 않는다.
- 작성자만 자기 전시를 수정하고 삭제할 수 있다는 규칙과 비공개 전시의 접근 제한은 애플리케이션 코드가 아니라 DB의 행 수준 접근 제어에서 강제한다.
- 로그인은 Google 계정으로만 받는다. 비밀번호를 직접 보관하지 않는다.
- 업로드된 파일은 저장 시점부터 비공개다. 관람자용 사진 접근 주소는 서비스가 그 파일이 딸린 기록의 현재 공개 상태를 확인한 뒤에만 발급한다.
- 공유 해제나 전시 삭제가 완료되면 관람자의 전시 접근과 관람자용 사진 주소의 신규 발급을 즉시 차단한다. 공유를 해제해도 작성자는 자기 전시와 사진을 계속 볼 수 있다.
- 관람자용 사진 주소는 발급 시점부터 최대 5분 동안만 유효하다. 이미 발급된 주소에 대한 후속 요청은 남은 유효기간 동안 허용하되, 서비스·CDN 캐시를 포함해 공유 해제나 삭제 완료 후 최대 5분 안에 차단되어야 한다.
- 공유 링크는 기록에 묶인다. 공개를 껐다 켜도 같은 주소가 같은 기록을 가리키고, 공개 상태 값만 바뀐다.
- 초기 설정은 프로젝트에 설치된 `setup-supabase` 스킬을 따른다. 이 스킬은 Supabase가 배포한 공식 스킬이 아니므로 공식 문서와 충돌하면 공식 문서를 우선한다.

## Boundaries

- 어떤 테이블을 두고 어떤 컬럼을 갖는지는 정하지 않는다. 스펙의 수용 기준을 만족하는 선에서 구현이 정한다.
- 전시 문구를 생성하는 AI 호출 경로는 이 결정의 범위가 아니다. `ai-gateway` 계약을 따른다.
- 사진 접근 차단은 해제·삭제 이후의 요청에 적용한다. 이미 사용자 기기에 내려받은 사진을 회수하는 것은 범위 밖이다. 저장소에서 파일을 실제로 지우는 시점과 관람자 접근 차단 시점은 구분한다.

## Why

전시는 로그인한 사람의 소유물이고, 공개 범위에 따라 접근이 달라지며, 사진 파일이 함께 붙는다. 이 셋을 서로 다른 서비스로 나누면 권한 규칙이 서비스 경계마다 흩어지고, 어느 한 곳만 어긋나도 남의 전시가 보이거나 비공개 전시가 새어 나간다. 하나의 서비스가 계정과 행 수준 권한과 파일 접근을 같은 사용자 신원으로 묶으면 규칙을 한 곳에서 기술하고 검증할 수 있다.

권한을 애플리케이션 코드에만 두면 새 화면이나 새 조회 경로가 생길 때마다 같은 검사를 다시 작성해야 하고, 한 곳을 빠뜨리면 그대로 유출이 된다. DB에서 막으면 경로가 늘어도 규칙은 하나로 남는다.

파일은 기록과 다른 경로로 전달되기 때문에 따로 막지 않으면 권한이 한쪽에서만 지켜진다. 비공개 기록에 딸린 파일이 주소만으로 열리면 기록을 막아둔 의미가 없고, 사용자가 공유를 꺼도 파일은 계속 열려 있다. 사용자가 무엇을 보여줄지 되돌릴 수 있어야 하므로 파일도 기록과 같은 공개 상태를 따라간다.

관람자에게 이미 발급한 사진 주소의 즉시 폐기 대신 최대 5분의 유예를 허용해 파일 전달 경로를 단순하게 유지한다. 공유 해제와 전시 삭제에는 같은 시간 기준을 적용하며, 전시 접근과 새 주소 발급은 바로 막는다. 주소의 유효기간만 짧게 설정해도 CDN 캐시가 더 오래 응답할 수 있으므로, 캐시를 포함한 실제 후속 요청이 5분 안에 차단되는지 확인한다. [Supabase Smart CDN 문서](https://supabase.com/docs/guides/storage/cdn/smart-cdn)에서 주소 만료와 캐시의 차이를 확인할 수 있다.

공유 주소를 기록에 묶은 것은 주소 체계를 한 겹으로 유지하기 위해서다. 공개를 켤 때마다 새 주소를 발급하면 되돌릴 수 없는 차단을 줄 수 있지만, 기록 주소와 공유 주소가 갈라져 화면과 접근 정책이 각각 늘어난다.

Google 계정으로만 받으면 비밀번호 재설정과 메일 인증을 만들 필요가 없고 비밀번호를 보관하는 책임도 지지 않는다. 이 제품은 사용자가 충동적으로 열었다가 몇 분 안에 결과를 보는 흐름이라 진입 마찰이 곧 이탈이다.

## Reconsider when

- 한 서비스에 묶인 탓에 필요한 데이터 모델이나 권한 규칙을 표현하지 못하는 상황이 반복될 때
- 사진 저장 비용이나 전송량이 별도 저장소를 둘 만큼 커질 때
- Google 계정이 없어서 쓰지 못하는 사용자가 실제로 나타날 때
- 한 번 나눠준 주소를 되돌릴 수 없이 끊어야 하는 요구가 생길 때
- 기존 사진 주소도 공유 해제나 삭제 직후 차단해야 하거나, 선택한 파일 전달 경로에서 캐시를 포함한 최대 5분 기준을 만족할 수 없을 때

## Still-rejected alternatives

- DB와 인증과 파일 저장소를 각각 다른 서비스로 조합하는 방식 — 권한 규칙이 서비스마다 흩어져 검증할 범위가 늘어난다. 권한 모델이 단순해지거나 특정 저장소의 이점이 분명해지면 다시 본다.
- 이메일과 비밀번호로 직접 회원가입을 받는 방식 — 재설정과 메일 인증 흐름이 함께 따라오고 비밀번호를 보관하는 책임이 생긴다. Google 계정이 없는 사용자가 실제로 막히는 일이 확인되면 다시 본다.
- 파일을 공개 저장소에 두고 주소를 추측하기 어렵게 만드는 방식 — 주소가 한 번 새면 회수할 수 없고, 사용자가 공유를 꺼도 파일은 계속 열린 채로 남는다.
- 공개를 켤 때마다 새 공유 주소를 발급하는 방식 — 기록 주소와 공유 주소가 갈라져 화면과 접근 정책이 한 겹 늘어난다. 되돌릴 수 없는 차단이 필요해지면 다시 본다.
- 모든 파일 요청을 서비스 경로로 받아 매번 공개 상태를 확인하는 방식 — 해제 즉시 닫히는 대신 파일 전송이 서버를 거친다. 즉시 차단이 요구사항이 되면 다시 본다.
